Dashboard — Low Stock & Restock Assistant

Show the real-time overview, low-stock alerts, and the Smart Restock Assistant ranked by sales velocity.

0:30 – 1:1040 sec
On Screen

Dashboard loads — "Welcome, {name}" with today's date

Stats grid shows: 8 Products, 3 Low Stock (red)

Scroll to Low Stock Alerts section

Point out: Palmolive (3/5), Lucky Me (8/10), Safeguard (0/5)

Scroll to Smart Restock Assistant

Show ranked list with "days left" badges — red for <3 days, neutral for <7

Narration

The dashboard gives an instant overview. We have 8 products, and 3 are flagged as low stock.

Low stock is defined as quantity at or below the buffer threshold — configurable per product.

Below that is the Smart Restock Assistant — a value-added feature. It computes each product's average daily sales velocity from historical stock logs, then projects how many days of stock remain. Products are ranked by urgency, so the shopkeeper knows exactly what to restock first.

Rubric beat: This segment covers Low Stock Alerts (requirement #10) and Smart Restock Assistant (value-add #1). The velocity calculation uses rolling averages from the stockLogs collection, not a flat threshold.

Let me register a new product. I click New Product, and this modal form captures everything: name, barcode, category, price, initial stock, and a buffer threshold for low-stock alerts.

Tip: Have a small product image ready on your desktop before recording. Keep it under 5 MB. The upload takes 1–2 seconds — the "Creating..." state covers the wait.

Barcode Lookup + POS Checkout

Search by barcode, build a cart, validate stock, and complete checkout via the outbox pattern.

1:50 – 2:5060 sec
On Screen

Click Sell in the nav → POS page loads

In the search bar, type: 4800735040015 (Chippy's barcode)

Chippy 110g appears in search results with stock badge

Click it → added to cart (qty 1, line total ≈25.00)

Clear search, type coca

Coca-Cola 1.5L appears — click it twice to set qty 2

Cart shows 2 items, total ≈195.00

Click Checkout (≈195.00)

Button changes to "Sale Staged" with checkmark (2.5 sec)

Cart clears

Narration

Now the point-of-sale. The barcode field is integrated — typing or scanning a barcode auto-fills the product. Let me type Chippy's barcode number.

There it is. I'll also add two Coca-Colas. The cart manages quantities and line totals in real time.

Before checkout, the system validates stock — if I tried to buy more than what's available, it would block the sale. That guard runs client-side and also inside the atomic transaction on the server.

When I hit checkout, the sale is staged to a pendingSales outbox — this is the offline-ready pattern. The actual stock deduction and sales record happen in an atomic Firestore transaction processed by a background sync.

Rubric beats: Barcode integration (#3), Virtual cart (#5), Stock validation (#6), Transaction execution (#7). The "Sale Staged" state confirms the outbox write succeeded.
Optional beat (10 sec if time allows): After the sale clears, quickly try to add Safeguard Soap (qty 0) to show the "Out of stock" error. This proves stock validation works. Skip if you're over 2:50.

6

Offline-Ready POS — The Outbox Pattern

The money shot. Go offline, stage a sale, come back online, watch it sync, verify in history.

3:05 – 4:1065 sec
On Screen

Open DevTools → Network tab (dock to bottom)

Set throttling to Offline

Red "Offline" pill appears at the bottom of the screen

Navigate to Sell (POS page)

Add Bear Brand Milk to cart (type "bear" in search)

Click Checkout (≈18.00)

Yellow banner appears: "Saving offline — 1 pending"

Cart clears, button shows "Sale Staged"

In DevTools, set throttling back to Online

Banner changes to purple: "Syncing..." with spinner

Banner disappears (sync complete)

Navigate to History — the offline sale now appears in the list

Narration

This is the feature I'm most proud of — the offline-ready POS. Let me simulate going offline.

The red "Offline" banner confirms the connection is down. Now, even without internet, I can still make a sale. I'll add Bear Brand Milk and check out.

See the yellow banner? "Saving offline — 1 pending." The sale was staged to a local outbox. The cart cleared normally — the cashier's workflow isn't interrupted.

Now I'll bring the connection back online. The sync processor picks up the pending sale, runs the stock validation atomically, commits the transaction, and clears the outbox.

And here's the proof — the sale I made while offline now appears in Sales History. No data lost, no overselling, no manual intervention.

Key beat: This is the highest-value segment. The narration explains the outbox pattern by name — stage offline, commit online, idempotent via status re-check. Mention "no overselling" explicitly.
Recording tip: Have DevTools already open before this segment starts. Dock it to the bottom so the app is still visible above. Practice the offline → online toggle once before recording — the sync happens fast.
Rubric beats: Offline-Ready POS (value-add #2). Also reinforces Transaction execution (#7) — the atomic transaction runs inside the sync processor, not at checkout time.
7

Architecture, PWA & Mobile View, Closing

Code editor tour, responsive design demo showing the PWA install banner, then sign off.

4:10 – 5:0050 sec
On Screen

Switch to code editor (VS Code)

Open src/lib/data-access/sales.ts — show commitSale() function

Briefly highlight the runTransaction block — stock check + deduction + sale write + pendingSales status update

Open src/contexts/sync-context.tsx — show the sync processor

Switch back to browser

Open DevTools → Toggle device toolbar (Ctrl+Shift+M)

Select a mobile viewport (e.g. iPhone 14 Pro)

The layout shifts: sidebar disappears, bottom nav appears with 4 tabs (Dashboard, Products, Sell, History)

Show the "Install Borcello Store" banner at the bottom with the Download button

Point to the manifest.json in the editor — "display": "standalone", theme color, icons

Exit device toolbar, end on dashboard at desktop width

Narration

Under the hood, the checkout uses a Firestore transaction that re-checks stock inside the write — so even under retry or concurrent access, it's idempotent and can't oversell.

The sync context runs the processor on load, every 30 seconds, and whenever the device comes back online. Conflicts are flagged for manual review.

The app is fully responsive. On mobile, the sidebar collapses into a bottom navigation bar — same four destinations, touch-optimized.

And it's a Progressive Web App. The install banner prompts users to add it to their home screen. Once installed, it opens in standalone mode — no browser chrome, just the app. The service worker caches the app shell for instant loads.

That's Borcello Store — a lean, offline-capable, installable Sari-Sari Store system built on Next.js and Firebase. Thank you.

Recording tip: Have VS Code and the browser side-by-side. For the mobile demo, use Chrome's device toolbar (Ctrl+Shift+M) — it simulates a phone viewport and triggers the PWA install prompt. The install banner only fires if the app meets PWA criteria (manifest + service worker + HTTPS or localhost).
Code to have ready: Have these files open in tabs before recording: sales.ts, sync-context.tsx, and public/manifest.json. The manifest shows "display": "standalone" and the icon sizes.
Note: The install banner fires from Chrome's beforeinstallprompt event. If it doesn't appear during recording, mention it verbally and show the manifest.json as proof. The banner may not trigger in incognito or if the app was already installed.
