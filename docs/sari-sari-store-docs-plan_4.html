01Findings on the source repo

Before planning anything, here's what suarez-food-hub actually is, so the rest of this plan is grounded in reality rather than in the repo's name.

It's a Turborepo/pnpm monorepo with four separate Next.js apps (customer ordering, admin dashboard, kitchen staff, rider delivery PWA), a 15-model Prisma schema against Postgres/Supabase, GCash/Maya payment flows, rider commission and cashout logic, live GPS broadcasting via Supabase Realtime, and PSGC address seed data for the Philippines. There is no barcode scanning anywhere in the codebase.

⚑ Flag — scope mismatch The assignment's Sari-Sari Store path asks for one shopkeeper-facing tool: register products, add stock, scan-and-sell, view sales history, flag low stock. This repo is a multi-role delivery marketplace. Stripping it down to size means deleting the large majority of it — which is more work, and more risk of leftover complexity, than building the small app fresh.
✓ What's still worth keeping The admin/inventory page's low-stock highlight pattern (red when quantity ≤ buffer_quantity, default buffer of 5) is almost exactly what the assignment asks for, and the Tailwind + shadcn/ui setup in packages/ui is reusable styling scaffolding. Logos and brand assets carry over fine too.

02App choice & platform justification

Locked in: Web (Next.js), installable as a PWA. This is the write-up for assignment task #2.

App: A — The Sari-Sari Store System

Chosen over the Explorer Discovery App because it maps directly onto a real business context and produces a genuinely useful administrative tool rather than a novelty GPS game.

Platform: Web (Next.js) as an installable PWA

  • Hardware — barcode scanning: a counter-based scan via getUserMedia + a JS barcode decoder covers a fixed-counter use case without a native camera pipeline. Documented trade-off: ML Kit's native Android integration is more robust for continuous fast scanning — noted here rather than glossed over.
  • Hardware — product photos: <input type="file" accept="image/*" capture="environment"> opens the device camera directly, the web equivalent of Android's Intent-based camera capture.
  • Accessibility & reach: works from any device with a browser, no install required to try it — and layered with a PWA manifest + service worker, it installs to the home screen and opens full-screen like a native app, giving the native feel without app-store distribution friction.
  • User needs: a single owner/cashier on one counter device benefits from instant updates and a build that's trivially demoable from any browser for the video submission.
  • Fallback path: if the rubric turns out to require native Android APIs by name, the Firestore data model and business logic stay identical — only the presentation layer would move to Kotlin + Jetpack.

04Data model (Firestore)

Five collections instead of fifteen models. Firestore is document-based — no joins, so category/product data is denormalized where it's read together.

CollectionKey fieldsNotes
products name, barcode, categoryName, unitPrice, quantity, bufferQuantity, imageUrl, createdAt, updatedAt Low-stock = quantity ≤ bufferQuantity, mirrors the source repo's pattern.
categories name Small, flat list — no nested subcategories needed.
sales items[] {productId, name, qty, unitPrice, lineTotal}, total, cashierId, cashierName, createdAt One document per completed transaction; items embedded, not a subcollection.
stockLogs productId, type ('restock'|'sale'|'adjustment'), delta, resultingQuantity, note, actorId, createdAt Audit trail — powers the Smart Restock Assistant in §7.
users displayName, role ('owner'|'cashier') Mirrors Firebase Auth UID; role also set as a custom claim for security rules.

05Data access & the ORM decision

No real ORM exists for Firestore — it's schemaless NoSQL, so there's nothing to generate a client from.

  • Fireorm — decorator-based repository pattern, Prisma-ish syntax. Thinly maintained, and fights against Firestore's real-time onSnapshot listeners.
  • firestore-simple — lighter wrapper, similar trade-offs.
✓ Recommendation Skip both. Use the Firebase JS SDK directly, wrapped in a handful of typed functions per collection, validated with Zod. Idiomatic, keeps real-time listeners simple, least moving parts. 
// lib/data-access/products.ts
export async function addStock(productId: string, delta: number, actorId: string) {
  const ref = doc(db, "products", productId);
  await runTransaction(db, async (tx) => {
    const snap = await tx.get(ref);
    const current = snap.data()!.quantity as number;
    tx.update(ref, { quantity: current + delta, updatedAt: serverTimestamp() });
    tx.set(doc(collection(db, "stockLogs")), {
      productId, type: "restock", delta, resultingQuantity: current + delta,
      actorId, createdAt: serverTimestamp(),
    });
  });
}

07Value-added features — locked in

Revised design: checkout stages to a pendingSales outbox (works offline), a processor commits each one through the real stock-validation transaction once online.
